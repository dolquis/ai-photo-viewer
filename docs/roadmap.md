# 実装ロードマップ

引継ぎ文書 14.4 に対応。Phase 0〜7 に分割し、各フェーズで目的・実装内容・
完了条件・リスクを定義する。MVP は Phase 1〜4 に相当する。

各フェーズは前フェーズのインフラ（DB・ジョブキュー・推論抽象）の上に積み上げる。

---

## Phase 0: 技術検証

- 目的: 主要技術の実現性とパフォーマンスを実測で確認し、設計の前提を固める。
- 実装内容: `docs/poc-tasks.md` の PoC 群（画像表示性能、サムネイル生成、
  SQLite、pHash、ONNX 埋め込み、ベクトル検索、顔検出、自然言語検索）。
- 完了条件: 各 PoC で性能数値を取得し、技術選定（`docs/tech-selection.md`）を確定。
- リスク: Avalonia のグリッド仮想化性能、ONNX EP のデバイス互換性。
  → 早期に CPU フォールバックの実用性を確認する。

## Phase 1: 高速画像ビューワー + DB + サムネイル

- 目的: AI 機能の土台となる閲覧体験とインデックス基盤を完成させる。
- 実装内容: フォルダ走査、`Images` テーブル、サムネイル生成・キャッシュ、
  仮想化サムネイルグリッド、画像ビューア（拡大縮小回転・前後移動・EXIF 表示）、
  ファイル監視による変更検知、ジョブキュー基盤。
- 完了条件: 数万枚フォルダで体感ひっかかりなくスクロール（受け入れ条件 AC-1）。
  閲覧操作がブロックされない。
- リスク: 大量サムネイルのメモリ管理。→ LRU キャッシュと遅延読み込みで対処。

## Phase 2: 重複検知 + 類似画像検索

- 目的: 内容ベースの整理機能の第一歩。
- 実装内容: 完全一致ハッシュ、pHash/dHash、重複グループ生成、重複管理画面、
  画像埋め込み生成（ONNX）、ベクトル索引、類似画像検索 UI。
- 完了条件: 拡張子/解像度/圧縮違いの重複が検出され、スコア付きで提示される。
  類似検索が 10 万枚想定の設計で 1 秒以内目標を満たす。
- リスク: ベクトル索引の方式選定（HNSW vs `sqlite-vec`）。→ Phase 0 PoC-6 で決定。

## Phase 3: 自然言語検索 + 自動タグ

- 目的: 「文章で探す」体験の実現。
- 実装内容: テキスト埋め込み、自然言語検索 UI、タグ付けモデル、`Tags`/`ImageTags`、
  AI/ユーザー確定/除外タグの区別、タグ修正 UI。
- 完了条件: 「夜の神社」等の検索が類似度順に妥当な結果を返す。タグ誤判定を修正できる。
- リスク: 埋め込みモデルの日本語クエリ精度。→ 多言語対応モデルを選定。

## Phase 4: 顔検出 + 人物グループ化

- 目的: 人物軸での整理。MVP の完成。
- 実装内容: 顔検出、顔特徴量抽出、クラスタリング、`Faces`/`Persons`、
  人物管理画面（名前付与・統合・分割・非表示）。
- 完了条件: 同一人物が概ね同一クラスタにまとまり、ユーザーが補正できる。
  顔特徴量がローカル保存に限定される（受け入れ条件 AC-7）。
- リスク: クラスタリング精度と誤統合。→ ユーザー補正 UI を必須とし全自動命名はしない。

## Phase 5: OCR + スクリーンショット検索

- 目的: 文字情報での検索。
- 実装内容: OCR モデル、`OcrResults`、OCR テキスト検索、ビューアでのテキスト選択・コピー。
- 完了条件: スクリーンショット内のエラー文等が検索でヒットする。
- リスク: 日本語 OCR 精度・処理コスト。→ 信頼度しきい値と領域座標を保持。

## Phase 6: 画質診断 + ベストショット選定

- 目的: 品質軸での整理支援。
- 実装内容: 画質評価モデル、`QualityScores`、状態ラベル付与、
  連写/類似群からのベストショット候補提示。
- 完了条件: ブレ/ピンボケ/白飛び等が妥当に判定され、削除候補・推奨が提示される。
- リスク: 主観的な「良い写真」の評価。→ ユーザーが最終判断する位置づけを徹底。

## Phase 7: アップスケール/ノイズ除去 + 共有前チェック

- 目的: 軽い AI 補正と差別化機能。
- 実装内容: アップスケール/ノイズ除去（非破壊・派生画像ツリー）、
  破綻検出、共有前プライバシーチェック（顔/ナンバープレート/個人情報検出、
  EXIF/GPS 削除、ぼかし、共有用コピー出力）。
- 完了条件: 補正が非破壊で行われ、共有前に個人情報が警告される。
- リスク: 補正のやりすぎによる破綻。→ 破綻検出と適用前プレビューを設ける。

---

## フェーズ横断の方針

- 各フェーズで `IJobQueue` にジョブ種別を追加し、解析パイプラインを段階的に拡張する。
- 解析結果には常にモデル名・バージョンを記録し、将来の再解析に備える。
- UI と推論実装の疎結合を維持し、モデル・デバイスを差し替え可能に保つ。
- MVP（Phase 1〜4）の肥大化を避け、後続機能を MVP に持ち込まない。
